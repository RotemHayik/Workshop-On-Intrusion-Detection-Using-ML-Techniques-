# Execution decisions and limitations

The accepted Part 2 draft and its frozen 42-feature roster, recording splits and representations are the starting point. No Part 2 content was rewritten. Local project files and the Drive Rotem folder were read or copied; their originals were not modified.

The Part 2 protocol listed candidate ranges. For the available four-core CPU and 8 GB RAM, this implementation predeclared four one-factor sensitivity configurations per model rather than claiming an exhaustive Cartesian grid. The exact executed configurations are in `03_config/experiments.json`. Two further IF feature-removal experiments were justified by Validation error evidence. Three seeds were run for each selected neural architecture; seed 42 was fixed for held-out testing.

Early stopping selects an epoch by Validation AUPRC with minimum improvement 0.00001, patience 8 and a 24-epoch cap. The operating threshold is then selected separately by maximum Validation recall under FPR <= 1%, with fewer false positives and a stricter threshold breaking ties. This separates ranking optimization from operating-point selection. The retained epoch and complete learning curve are saved with each checkpoint.

An initial packed-sequence LSTM profiling run was interrupted after one epoch because its CPU kernel took about 136 seconds per epoch. The final implementation groups a minibatch by exact valid sequence length and runs dense LSTMs only on real timesteps. The incomplete run was restarted from the same seed; it was not included in the result table. Padding-invariance tests verify that padding cannot influence backward-direction states. Completed final runs took roughly 10–30 seconds per epoch depending on width, depth and concurrent workload. The historical training log preserves the interrupted profile and the restart.

The local LLM ran concurrently with some seed repeats. Its measured request times include CPU contention. Detector inference times include data/model loading and were measured once per split, so they are descriptive timing observations rather than a controlled microbenchmark. The cascade was evaluated by routing aligned, precomputed predictions. It implements the declared decisions exactly but does not establish a measured end-to-end speedup from skipping neural inference in a live service.

Vanilla GraphSAGE uses mean neighborhood aggregation, normalized hidden vectors and mean graph pooling. Stored edge attributes are not consumed. The proxy graph links clients, servers, base domains and subdomains within each window. It is not GraphTunnel's full recursive resolver graph. Model outcomes therefore support a comparison of graph-based behavioral representations, not an exact reproduction of that publication.

The Validation-gated LLM override remained enabled in the frozen experiment because both selected Validation cases were correct. Held-out Test exposed one harmful override, while External Test exposed three beneficial overrides. This is reported without changing the policy after Test. A future deployment should require a larger, independent, source-diverse arbitration validation set before enabling automatic overrides. The current package is an experimental submission, not a validated live blocking service.

No new synthetic traffic was generated. Class imbalance was handled through class/recording weights and balanced sampling, with unchanged Validation/Test populations. The underlying problem remains source-label confounding: almost all benign Train windows come from one capture ecosystem. External Test is malicious-only, so specificity on unseen benign traffic remains unmeasured there.
